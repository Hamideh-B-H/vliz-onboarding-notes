# VLIZ GitHub Management Conventions

Summary of the official VLIZ Open Science conventions for managing GitHub repositories. Source: open-science.vliz.be/conventions/github-management

## 1. Repository naming

- Use kebab-case: all lowercase letters and dashes (e.g. name-of-repo)
- Tag repos with relevant topics in the About section (e.g. python, docker-compose, react)
- Releases use git tags following Semantic Versioning (major.minor.patch, no 'v' prefix)
- Every repo needs a LICENSE file — MIT for source code, CC-BY for datasets

Naming patterns by repo type:

| **Type** | **Pattern** | **Example** |
| --- | --- | --- |
| Python packages | py-* | py-sema |
| GitHub Actions | *-action | rohub-sync-action |
| GitHub Pages Actions | *-pages | space-to-pages |
| RO-Crates | *-crate | observatory-bpns-crate |
| Web components | *-widget | rocrate-preview-widget |

## 2. Branches

Every repo should have two default branches:

- main — release-ready code
- gh-pages — documentation (auto-maintained by a documentation workflow)

New work happens on a separate branch, named:

`{category}/{description}`   e.g. `fix/connection_bug`

Allowed categories: fix, feature, refactor, chore, docs (more can be added if needed). The description part uses snake_case.

## 3. Commit messages

Follow the Conventional Commits specification:

`<type>: {action} {what} {where} {why}`

ex: `refactor: change args in funcA to allow typehinting`

Allowed types: build, chore, ci, docs, feat, fix, perf, refactor, revert, style, test. Additional detail can go in the commit body/footer per the Conventional Commits spec.

## 4. Pull requests

**Direct pushes to main are not allowed.**

Every change goes through a branch and a pull request. When opening a PR:

- Give it a descriptive name (can mirror the branch name)
- Write a description explaining the purpose
- Use GitHub keywords to link related issues where relevant

Before a PR can be merged, it must:

- Receive at least one approval
- Pass all checks: linting, testing, test coverage

Commits within a PR should tell a cohesive story — each one clear, focused, and self-contained.
