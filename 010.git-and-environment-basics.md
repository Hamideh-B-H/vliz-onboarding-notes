# Git and environment basics (from running populate-action locally)

## Core git commands

| Command | What it does |
|---|---|
| `git status` | Shows current branch, sync status with GitHub, and what's changed/staged/untracked |
| `git branch -vv` | Shows which branch you're on and whether it's tracking a remote |
| `git log --oneline` | Short history of past commits |
| `git add <file>` | Stages a specific file |
| `git add .` | Stages everything changed in the folder |
| `git commit -m "message"` | Saves a snapshot of staged changes, locally |
| `git push` | Uploads commits to GitHub (once tracking is set, no need for `origin main`) |
| `git pull` | Downloads and merges changes from GitHub |
| `git init` | Turns a folder into a git repo (local only, no GitHub involved yet) |
| `git remote add origin <url>` | Links a local repo to a GitHub repo |
| `git branch -M main` | Renames current branch to `main` |
| `git push -u origin main` | Pushes and sets up tracking, so future `git push`/`git pull` don't need `origin main` |

**The core cycle:** `git add` → `git commit -m "..."` → `git push`. Think of it like a letter: add = deciding what goes in the envelope, commit = sealing it with a label, push = mailing it.

## Environment variables

An environment variable is information the operating system makes available to any running program, without hard-coding it into the program's own code.

Why they exist: values that change per machine/person/situation (secrets, file paths, config) shouldn't be hard-coded into shared code.

In Python, code reads them with `os.getenv("VARIABLE_NAME")`. In PowerShell, you set one for the current terminal session with:
```
$env:VARIABLE_NAME = "value"
```
These only last for that terminal window — closing it clears them.

**How to spot which env vars a script needs:** scan for `os.getenv(...)` or `os.environ[...]` near the top of the script, check for a `.env.example` file, check the Dockerfile's `ENV` lines, or check the calling workflow's `env:` section.

**Why GitHub Actions doesn't need these set manually:** GitHub automatically sets standard ones (`GITHUB_WORKSPACE`, `GITHUB_REPOSITORY`) before running a workflow. Custom ones (like `WATER_LOGSHEET_URL`) are set explicitly in the calling `workflow.yml`'s `env:` section — running locally means setting all of these ourselves.

## How to find dependencies for a repo

Check in this order:
1. **`Dockerfile`** — most reliable if present; `RUN pip install ...` lines show exactly what's installed
2. **`requirements.txt`** — plain list of packages
3. **`pyproject.toml`** — used by Poetry-based projects (declares deps under `[tool.poetry.dependencies]`)
4. **`import` statements** at the top of the script — cross-check which are built into Python (no install needed) vs external packages

## Virtual environments

An isolated, self-contained Python setup for one project, so installed packages don't clash across different projects.

```
python -m venv venv                    # create it
.\venv\Scripts\Activate.ps1            # activate it (Windows PowerShell)
pip install <packages>                 # installs into this isolated env only
```

## Worked example: running populate-action locally

1. Cloned `populate-action`, read `action.py`, `Dockerfile`, `entrypoint.sh`
2. Created a `venv` inside `populate-action`, installed `pandas`, `openpyxl`, and `emobon-dm-tools` (from GitHub, pinned to `@release/v0.1.0`)
3. Found the 3 required Google Sheets URLs in `governance-crate/logsheets.csv` (BPNS row)
4. Created an empty `workspace/` folder (since the script deletes everything in `GITHUB_WORKSPACE` before writing)
5. Set 5 environment variables (`GITHUB_WORKSPACE`, `GITHUB_REPOSITORY`, and the 3 logsheet URLs)
6. Ran `python action.py` — produced 8 CSV files in `workspace/logsheets/raw/`

Full details and the actual URLs used are documented in the `bpns-workflow-local` repo's own README.
